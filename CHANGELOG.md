# Changelog

All notable changes are listed here, newest first. The version numbers follow [Semantic Versioning](https://semver.org): while the first number is 0, the
program is not yet in its final form and any release may change how it is set up. See "Versioning" in [CONTRIBUTING.md](CONTRIBUTING.md).

## Unreleased

- **A log file, and a button to download the log (#46).** `-log-file PATH` (or `BOOTLACE_LOG_FILE`) also writes the log to a file that keeps to `-log-size` MB (default 5): when it is full it becomes `PATH.1` (the one older file that is kept) and a new one starts, so a restart of a container or of Windows no longer loses the log. The password made up at the first start is shown on the console and in the web log but never written to the file. The Log page has a "Download the log" button.
- **A failed start no longer ends at the PC's disk (#53).** After "Booting did not work" the message stays for 20 seconds (a key press ends the wait), then the menu is shown again, on a page without the PC's rule and without a timeout, so a PC that is set to start pfSense by itself waits at the menu instead of silently booting its disk. Before, the menu script went back to a `${self}` setting that iPXE does not have (it ended at the iPXE shell) and a rule's script waited for a key for ever. The messages "this ISO is still being unpacked, try again", "could not be unpacked", "needs the iSCSI server" and "FreeBSD starts on UEFI only" also come back to the menu after a few seconds instead of leaving the network boot. Going to the disk is now only the explicit "Boot from this PC's own disk" line.
- **Names for PCs (#37).** The PCs page has a Name / Rename button per PC. The name is kept with the MAC address (also when the PC is forgotten from the list), is shown first in the list, is searchable and is used in the log lines for that PC. When a PC offers a host name in its DHCP request (option 12) or an asset tag in its SMBIOS, the page shows it as a suggestion that one click takes over; a name typed by a person always wins, and names that come from a PC are length-limited, escaped and never used to decide anything (rules stay by MAC address). Reverse-DNS and NetBIOS names are not looked up.
- **Leftovers are cleaned up by themselves (#45).** A minute after the start and then once a day the server removes: partial files in `<library>/.bootlace/incoming` that no import job owns and that were left alone for a day; cache entries (unpacked images, copies of `boot.wim`, in the container's cache folder and in the library's) of ISOs that are no longer in the library; and records of the checksum index for files that are gone. It only looks inside those folders, never touches an ISO or any other file, does nothing while the library is not available (an unmounted network folder looks empty), and writes every removal to the log.
- **Tuning on the Menu page (#31).** New "Tuning" card: (1) *patterns that keep ISOs out of the menu*, one per line, compared with the ISO's path in the library without regard to case (`old/` is a folder, `*beta*` any path with beta in it, `win11.iso` one file; `*` any text, `?` one character); a file hidden this way is still listed on the ISOs page, marked "by a pattern"; (2) *largest TFTP block*, for switches and firmware that only work with small blocks (0 follows each PC; at least 512); (3) *TFTP blocks sent ahead* to FreeBSD's loader, which now also can be set in the web interface (it wins over `-tftp-window`). The values apply to the next transfer, no restart.
- **Menu accent colour (#27, first part).** The Tuning card on the Menu page has a "Colour of the highlighted line": Gola red (default), green, yellow, blue, magenta, cyan or white. It colours the chosen line and the section headings, and the picture menu of a UEFI PC too once a colour other than the default is set. The logo and the menu heading are still fixed; that part of the issue is left open for a decision.
- **Self-test button (#44).** The Server page has a "Run the self-test" card. From the server's own address it asks for what a PC asks for, one step at a time: the boot script and the menu (which also proves the local-network rule lets the server's own address through), the first 16 bytes of an ISO, a TFTP file, the Windows share's first message (the SMB 1 negotiate that Windows' set-up starts with, answered in SMB 2), the network disk's greeting and the iSCSI port. A step that fails says what to look at; a service that is switched off is skipped. A firewall in front of the computer cannot be seen this way, and the page says so.
- **Look for another PXE or DHCP-boot server (#43).** A card on the Server page ("Other servers on the network") sends the question a PC's firmware sends, a PXE DHCP discover from the server's own address to its network's broadcast address, listens for four seconds and lists every answer: the address, the boot file, and what it is in words (this server; the network's own DHCP server, which is normal next to the proxy mode; another server that answers network boots, which competes). With `-dhcp full` any other DHCP server is reported as a conflict too. It runs when the button is pressed and once ten seconds after the start (the result is written to the log as a warning when something competes); the last result is shown when the page opens. It needs to hear broadcasts: a server in a container needs the host network, and a DHCP client of the same computer holding UDP port 68 is shared with, not displaced.
- **Library speed test (#40).** A card on the Server page writes a test file (up to 512 MB and at most a tenth of the free room, random data so that nothing compresses it, flushed to disk) in the library and in the container's own cache folder, reads it back, removes it, and says how fast each is and how many installs at once the read speed carries at 25 MB/s each. Where the operating system's file cache can be emptied before the read (Linux, as root) the read speed is the disk's; otherwise the page says the read may come from memory. It refuses to run while PCs are using the server unless the person agrees, and runs one test at a time. (Running it once when the library is chosen and keeping the result is left for later.)
- **Settings backup, restore, and a copy in the library (#41).** (1) Whenever the settings change a copy without secrets is written to `<library>/.bootlace/settings.json`. A new container given the same library finds a copy it has not decided about and the Server page asks: restore the library's settings, or keep these and replace the library's copy; until the person decides, the library's copy is never overwritten. (2) *Download a backup* packs `settings.json`, the list of PCs and a small manifest (version, date) into one zip; *Download with the passwords* also holds the web interface's password hash and the share's password, for moving to another machine (the page warns that the file is to be kept like a password). (3) *Restore from a backup file* shows what it holds against what the container has (rules, PC names, ISO titles, hidden ISOs, arguments, patterns, PCs) and asks before replacing; the library choice always stays, and so do the passwords unless the backup holds them. (4) A backup made by a newer version, a file that is not a zip or holds anything unexpected, or settings that do not pass the checks are refused with a message and nothing is applied.
- **Wake a PC from the PCs page (#23, first part).** Every PC in the list has a "Wake" button that broadcasts a Wake-on-LAN magic packet for its MAC address on the server's network (to the network's broadcast address and to 255.255.255.255, UDP port 9). The PC starts only if its network card and firmware are set to wake on that packet. Scheduled starts are not done yet.
- **A full cache removes the least recently used entries (#48).** When a cache place is full (the container's own folder over its limit, or the library's disk out of room) the server now removes the entries that were used least recently and that nothing is using, oldest first and only as many as needed, instead of failing: with "the container only" when the folder is over its limit, with "the library" when its disk is full, and with "the container, then the library" when both are full. An entry counts as used when the menu, a download or a disk reads it (its file time is refreshed), and it is never removed while a PC is using its ISO or for 30 minutes after its last use; files that are not named like cache entries (and partial files) are never touched. The Server page lists the entries, oldest first, with what is kept and why, and says so plainly when nothing could be removed (the size of the container's folder limits how many different installs can be prepared at once).
- **A first-start guide (#42).** A new installation opens on "Start here", four short steps: set your own password (the one made up at the first start is replaced; shown as done once you have chosen one, or given one with `-admin-password`), choose the library, review who may use the server, and "Run the checks" (the self-test and the look for other servers, with what the DHCP mode means). Finishing or skipping it makes the page go away for good; an installation that existed before this version is treated as having been through it. Everything the guide does is also on the normal pages. (The generated password is still written in the log: showing it in the page would let anyone who reaches the port log in.)
- **Verbose start-up, serial console, and the commands a PC gets (#28).** Under each ISO that is started from its own files, two switches and a fold-out: *Verbose start-up* takes `quiet`, `splash` and `rhgb` out of the kernel line and adds `loglevel=7 ignore_loglevel debug`; *Serial console* adds `console=tty0 console=ttyS0,115200n8` (the serial port last, so it is the kernel's main console) for a PC or virtual machine whose serial port is recorded; *Show the commands a PC gets* lists the exact iPXE commands of the entry, after the extra arguments and these switches. Applied at the next start of that ISO; both off removes the setting.

## 0.1.5 - 2026-10-23

- **FreeBSD, pfSense and OPNsense: reading the ISO by TFTP is several times faster.** FreeBSD's loader reads its kernel and the whole ISO by TFTP, one 1428-byte block at a time, and on the first real PC that took about 30 minutes for pfSense's 875 MB (a round trip through the firmware's network driver for every block). Bootlace now sends up to four blocks ahead of the acknowledgements to that loader (only to it: not to a client that asks for a window itself, and not to the firmware's own TFTP client), and sends the blocks again from the oldest one that is not acknowledged when the client says it missed one. `-tftp-window N` (or `BOOTLACE_TFTP_WINDOW`) changes the number; 1 turns it off. The log now says how long a large TFTP transfer took and its speed.
- **pfSense, OPNsense, FreeBSD: leave the PC's firmware clock alone.** With 0.1.4 the loader read the kernel and the whole ISO by TFTP (it takes a few minutes) and pfSense's kernel started, then stopped in its debugger right after `netgate0` at an address inside the firmware (the kernel's EFI clock, `efirtc`, is the next thing it starts). The boot settings that Bootlace adds now include `efi.rt.disabled="1"`, FreeBSD's switch for that, and `boot_verbose="YES"` so that the last lines on screen say more if it stops somewhere else.

## 0.1.4 - 2026-10-23

- **FreeBSD, pfSense and OPNsense: read the files by TFTP, not NFS.** A packet capture on the first real PC showed that after getting its address FreeBSD's loader asked this server's port 111 (the NFS port mapper) over and over and waited. FreeBSD's loader reads its files by NFS unless the DHCP root path starts with `tftp://`. The answer Bootlace gives to the loader's own address request now carries the root path `tftp://<this server>/`, so the loader asks for its files by TFTP, which Bootlace serves from the ISO.

## 0.1.3 - 2026-10-23

- **FreeBSD, pfSense and OPNsense: the loader's own address request.** On the first real PC the hand-off worked and FreeBSD's loader started, then stopped after "Setting currdev to net0:". The server's log showed why: the loader asks for an address again with a DHCP request of its own (it says PXEClient but sends no architecture), and Bootlace answered it like a PXE firmware, with a proxy answer that has no address. The loader needs an address *and* the name of the server in one answer. Bootlace now answers that request (and only that one, from a PC that chose a FreeBSD ISO a moment ago) with the address the PC already had, this server as the server to read from, and the network mask; a request meant for the network's own DHCP server is left alone. Not yet confirmed on real hardware.
- The Proxmox script's closing message and `docs/proxmox.md` told people to run `pct exec <number> update`, which fails ("No such file or directory"): `pct exec` does not search `/usr/local/bin`. They now give the full path, and say that `pct enter <number>` needs no password (the container console asks for one because the container's root has none).

## 0.1.2 - 2026-10-23

- **FreeBSD, pfSense and OPNsense on a PC with more than one network card.** The hand-off told the server the address and MAC of the *first* card (`net0`), not of the card that got the address, so the server answered "HTTP 4xx" and the PC went on to its disk. It now uses the card that is in use. Found on the first real UEFI PC (two network cards).
- **Proxmox script: no needless template download.** A Debian 12 or 13 template that is already on the host (on any storage that holds templates) is used as it is; the newest one on offer is downloaded only when there is none. (The script itself is fetched from `main`, so this applies to the next install without a new release.)

## 0.1.1 - 2026-10-23

- **Security fixes found by `govulncheck`.** The `.xz` reader is updated (v0.5.12 to v0.5.17: a damaged packed file could use up memory), and the build needs Go 1.27.3 (a fix in the certificate checks used when a file is downloaded from a web address).
- The Proxmox documentation now says plainly that the community-scripts project cannot take Bootlace until it is six months old with 600 stars (#50); `tools/proxmox/bootlace-lxc.sh` is the way to install in a container.

## 0.1.0 - 2026-10-23

The first release. What the program does is listed at the end of this section.

- **Legal and publishing.** The additional terms are now final: attribution, modified versions must say they are modified, and no rights to the names; the rules for the names are in `TRADEMARKS.md`. `NOTICE` carries a written offer of the source code of the GPL programs inside the release (iPXE, wimboot, GRUB), and every release has them as `bootlace-<version>-third-party-sources.tar`. `SECURITY.md` says how to report a problem privately.
- **Signed releases.** `SHA256SUMS` is signed (`SHA256SUMS.sig`, made with OpenSSH's `ssh-keygen -Y sign`); the public key is the file `allowed_signers`, and [docs/verifying.md](docs/verifying.md) shows how to check a download. `tools/release.sh` signs and refuses to make a release without a key.
- **The first password is easy to find.** It is made up at the first start and written once in the log; the Proxmox scripts now show it at the end of the installation, and the Docker, Proxmox and web interface documentation say where to look and how to set a new one if it is lost.
- **Docker.** A `Dockerfile` (42 MB image, Alpine, with wimlib for Windows with Secure Boot) and a real `deploy/docker-compose.yml` (host networking, a volume for the settings, a folder for the library). Every option of `bootlace serve` can be set as an environment variable `BOOTLACE_<NAME>`, and `bootlace health` is the container's health check. The server's address is now the one of the computer's default route, not the first private address (inside Docker that was the Docker bridge). (#11)
- **Release files.** `tools/release.sh` makes the archives for Linux (amd64, arm64) and Windows, a `SHA256SUMS` file and the Docker tags of a version. The archives are made by `tools/archive`, the same on every computer: owner 0 (an archive that names the builder's user cannot be unpacked by root in an unprivileged container), the program executable, one fixed time, so the same sources give the same archive. (#11)
- **Proxmox, own script rewritten.** It asks a few questions (container, network, and where the ISOs are: in the container, a host folder, or an SMB or NFS share), takes the program from the release files and checks its checksum, and writes the container's Notes with a link to gola.tn. A share is mounted on the host with an automount, so it does not matter whether the NAS starts before or after the container; the container follows it, and Bootlace waits for it. Tested on Proxmox VE 9.2, including a hard NFS mount that disappears and comes back. (#11)
- **`update` in the container.** Type `update` in the container's console: it checks the version, asks before restarting the server, verifies the download, and goes back to the old version if the new one does not answer. (#11)
- **community-scripts.** The files for the Proxmox VE Helper-Scripts (`deploy/community-scripts/`: ct, install and json), tested with their engine on Proxmox VE 9.2. (#11)
- **Library page.** Upload files, add a file from a web address, rename, move, make folders and delete, all in the web interface. A file is written to disk as it arrives and only put in place when it is whole; its first bytes are checked against its name; an optional SHA-256 or SHA-512 is verified; the same name, address, size or content is noticed before and after; nothing is ever replaced. Downloads are fetched by the server with a client that refuses local addresses at the moment it connects, resume after an interruption or a restart, and slow down while PCs are installing (a setting). Deleting is never recursive. The settings of an ISO follow it when it is renamed or moved. (#20)
- **Cache in two places.** Unpacked images and the copies of boot.wim go to the container's own small cache folder while it has room and then to `<library>/.bootlace/cache`; the size and the choice are settings on the Server page. (#20)
- **The login slides.** It lasts while something is done in the page (a transfer in progress counts, the page refreshing itself does not), ends after 30 quiet minutes, and never lasts longer than 12 hours.
- **Local network only.** Every service (web page and menu, Windows share, iSCSI, network disk, TFTP, DHCP) now refuses addresses that are not local (private ranges, loopback, link-local). More networks, or "from anywhere" with a confirmation, are set under Server in the web interface; refusals are counted there, and a public server address gives a warning. (#38)
- The ISO folder is now a **library**, chosen in the web interface (Server page, with a folder picker). It must be readable and writable and is recognised by a marker in its `.bootlace` folder: a missing network drive is never mistaken for it, and nothing is served or written then. `-iso-dir` only adds the library on the first start. (#36)
- The services PCs talk to can be started and stopped in the web interface, with a warning when PCs are connected; a port that is already taken is reported there instead of ending the program. The server stops after 30 seconds without the library and starts again by itself when it is back. (#36)
- Hidden folders and files (`.bootlace`, `._name.iso`) are never offered as ISOs.
- The Proxmox script now mounts the ISO folder read and write, and says what to do when the container cannot write to it.

What the program does:

- PXE network boot server in one program: proxy DHCP, TFTP, a web server, a network disk (NBD) server, an iSCSI target and a Windows file share, with iPXE for
  BIOS and UEFI built in.
- A boot menu made from a folder of ISO files and disk images (also packed `.xz`, `.gz`, `.zst`, `.bz2` and `.zip`); the files are never changed.
- Ubuntu, Debian, Fedora and relatives, Arch, openSUSE, Alpine, Proxmox VE, Tails, Windows (also with Secure Boot on), FreeBSD and many more start by name; other live
  ISOs are recognised from their own boot menus. Results per ISO: [docs/compatibility.md](docs/compatibility.md).
- A web interface to see the PCs, hide or rename ISOs, give a PC a rule, and read the log.
- A script that makes a Proxmox container with the server in it.
